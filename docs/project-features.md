# CodeAgent 项目功能说明

| 项目 | 内容 |
| --- | --- |
| 文档版本 | V0.1 |
| 编写日期 | 2026-11-06 |
| 适用范围 | 当前代码已实现功能，不代表生产就绪或全部人工验收完成 |
| 项目定位 | 本地桌面代码工程助手，辅助 Java/Python 项目的需求、设计、代码、测试和 Git 交付 |
| 维护原则 | 功能变更时同步更新本说明，并在文末追加修订记录 |

## 1. 系统组成

| 组成 | 实现与用途 |
| --- | --- |
| 桌面界面 | React、Vite、Tauri 2，提供项目接入、任务操作、文档与代码差异审核 |
| 本地服务 | Python 标准库 ThreadingHTTPServer，默认监听 127.0.0.1:8765 |
| 任务存储 | SQLite，保存任务快照、执行事件和错误信息 |
| 实时日志 | Server-Sent Events，推送当前任务的执行事件 |
| 模型接口 | OpenAI 兼容 chat/completions，支持本地 Ollama 等兼容服务 |
| 交付管理 | Markdown 文档、测试报告、变更记录和 Git 提交 |

## 2. 已有项目接入与文档基线

- 按本地路径扫描已有项目，识别 Java/Python、模块目录、候选源码、测试文件和构建工具。
- 读取 Git 仓库及分支状态。
- 生成产品需求、总体设计、详细设计三份 Markdown 草稿。
- 未配置模型时使用本地静态分析草稿；已有项目文档模型调用失败时可回退到本地草稿。
- 预览文档后明确确认，才写入目标项目的 docs 目录，追加变更记录并尝试 Git 提交。

静态扫描和模型推断不等于正式业务需求。用户仍需确认角色、交易边界、数据归属、接口和验收标准。文档基线写入尚未具备迭代流程同等完整的 Git 指纹保护。

## 3. 已有项目迭代

### 3.1 需求与影响分析

- 输入功能需求或缺陷描述，按关键词、目录和测试文件进行规则化影响分析。
- 生成预计修改文件、受影响模块、关联测试及迭代计划。
- 确认迭代计划后先提交计划，不直接修改业务代码。
- 调用模型生成完整文件草案，再单独审核代码和设计文档差异。

影响分析不是完整语义分析或运行时依赖追踪，结果需要人工复核。

### 3.2 差异审核与写入

- 统一展示代码、需求、总体设计和详细设计的 unified diff。
- 审核阶段冻结设计修订内容，确认前检查所有文件基线，再写入审核内容。
- 修改后执行关联测试，生成单元测试报告、受影响范围回归报告和变更记录。
- 测试通过后提交；测试失败保留现场，不生成完成提交。

两类测试报告目前基于同一次关联测试执行，并非两套独立测试。设计更新包含修订说明及待核对项，不保证已经完成业务语义级章节重写。

### 3.3 Git 安全控制

- 迭代开始要求已有 HEAD，工作区和暂存区干净。
- 记录 HEAD 与相关文件的 SHA-256 指纹，确认写入前重新核对。
- 暂存后检查文件集合，防止混入用户的其他文件。
- 检测到基线变化时终止，不覆盖并行修改。

## 4. 新项目创建

### 4.1 需求澄清与两阶段确认

收集以下结构化需求：

| 字段 | 内容 |
| --- | --- |
| users | 用户角色 |
| boundary | 交易或微服务边界 |
| workflow | 核心流程与输入输出 |
| acceptance | 验收标准 |
| constraints | 安全、数据及运行约束 |
| services | 可选 Java 微服务清单 |
| java_stack | 可选 Java 技术栈 |
| dependencies | 可选第三方 Maven 依赖清单 |

流程：输入目标与需求 → 补充澄清 → 评审三份文档 → 批准设计 → 生成并审核文件差异 → 再次确认创建 → 测试/打包 → 尝试首次 Git 提交。

- 必填需求缺失时禁止批准设计和创建项目。
- 文档评审、模型草案和差异预览不创建目标目录。
- 目标目录必须不存在，父目录必须存在，不允许嵌套在已有 Git 仓库中。
- 普通单模块项目可以创建固定示例骨架，但示例不代表业务目标已实现。
- 微服务和 Spring 项目必须先生成业务草案，不能直接创建旧示例。
- 创建失败保留文件，不自动清理；暂不支持新项目失败后的自动修复或重试闭环。

### 4.2 模型业务草案

- 将需求及设计材料发送到所配置的模型，返回完整源码和测试文件。
- 保留系统生成的构建配置及已批准文档，不允许模型任意写 POM、脚本和 Git 文件。
- 限制路径、文件类型、重复文件、文件数量和单文件内容长度；最终源码与测试集合最多 50 个文件。
- Java 预检包括包路径、公开类型名、重复公开类型、导入范围和 JUnit 注解等。
- 必须同时有源码和测试；模型不合规时拒绝，不把固定骨架冒充业务实现。

Java 预检是保守文本检查，不是完整编译器或安全检查；编译和测试以实际工具执行结果为准。

## 5. Java 与微服务技术栈

| 技术栈 | 已实现配置 |
| --- | --- |
| standard | Java 8、Maven、JUnit 4.13.2 |
| spring-boot | Java 17、Spring Boot 3.5.8、JUnit5、Mockito、Web 与测试 Starter |
| spring-cloud | Spring Boot 配置，加 Cloud 2025.0.0 BOM、OpenFeign、LoadBalancer |

### 5.1 微服务工程

- 支持 2 至 10 个不重复的小写服务名，以英文逗号分隔。
- 根 POM 聚合构建，各服务拥有独立 POM、源码、测试和 main 入口。
- 服务间不自动建立 Maven 源码依赖；接口、端口、数据归属需在需求中说明。
- Spring 服务生成独立 application.properties，默认端口自 8080 递增，可用 SERVER_PORT 覆盖。
- 模型提示要求独立 HTTP 入口及下游接口隔离；单元测试使用手写替身或 Mockito。

HTTP 行为、下游隔离和入口配置仍需审核，不仅凭文本预检确认。注册中心、网关、数据库、分布式事务、容器部署及跨服务契约测试尚未自动实现。

### 5.2 第三方依赖

- 以 JSON 数组声明 groupId、artifactId、version、scope 和 packages，最多 20 项。
- 支持 compile/runtime/test，当前统一应用到各业务模块。
- 限制固定坐标和版本，拒绝版本变量、区间、XML 输入、重复及覆盖系统管理依赖。
- 根据作用域校验源码导入；packages 为用户声明的允许范围，不自动证明真实依赖包含该包。
- 系统生成 POM 供审核，不自动新增私有仓库或任意构建插件。

尚不提供许可证、漏洞、恶意依赖及版本冲突的自动审计。固定 Spring 版本组合不代表持续安全支持承诺。

### 5.3 JDK 选择与打包

- Spring 新项目优先使用 CODEAGENT_JAVA17_HOME，其次 JAVA_HOME，要求完整 JDK17 或更新版本。
- 在创建目录前检查 javac 版本，不符合要求时拒绝。
- JAVA_HOME 和 PATH 仅传给构建子进程，不修改系统环境。
- Spring 新项目执行带精确测试类过滤的 Maven package；其他 Java 流程通常执行 test。
- 当前工具链选择针对 Spring 新项目，不能据此认定已有项目迭代会自动切换 JDK。

## 6. 测试执行与报告

| 工具 | 执行能力 |
| --- | --- |
| pytest | 按显式关联路径执行 Python 测试 |
| Maven | 从 Java 测试路径定位模块，按全限定测试类过滤；跨模块逐模块执行并汇总 |
| Gradle | 按类过滤，优先使用 Wrapper；跨模块暂不支持 |

- 未确定关联范围时不退化为全量测试。
- 优先查找模块或父目录的 Maven/Gradle Wrapper。
- Java 统计仅使用本次新增或更新的单元测试 XML，不把旧报告当成本次成功依据。
- 记录总数、通过、失败、错误、跳过、耗时、命令及输出。
- Java 进程退出成功但无有效报告或零用例时，不判定通过。
- Maven 多模块任一模块失败，整体不通过；不自动安装兄弟模块或推断依赖顺序。

生成测试通过不等于独立业务验收、服务启动验收或跨服务集成验收。

## 7. 模型生成增强

| 配置项 | 作用及限制 |
| --- | --- |
| max_repair_attempts | 0 至 2 次静态校验反馈修复，默认关闭；网络错误不自动重试 |
| staged_java_generation | 先源码后测试，测试请求携带真实源码，禁止修改源码，默认关闭 |
| compact_generation_context | 省略重复设计文档，保留结构化答案，默认关闭；可能损失文档独有信息 |
| max_tokens | 128 至 32768，部分服务把推理也计入额度；检测截断和空正文 |
| timeout_seconds | 模型请求超时设置 |

- 修复记录保存在 generation_attempts；每次重新校验，不降低路径和依赖限制。
- 分阶段全部成功才替换审核草案；失败保持原审核内容。
- 当前按阶段生成，不是逐文件生成；不包含编译错误反馈自动修复。
- 本地真实模型测试可记录请求、响应、耗时和错误，需显式开启。

## 8. 任务、日志与恢复

- SQLite 持久化任务与事件，默认 data/codeagent.db，可通过 CODEAGENT_DATABASE 指定。
- 历史任务可重新载入需求、文档、草案、报告和最近失败原因。
- 已完成任务拒绝重复确认写入。
- 已有项目测试失败可在现场快照未改变、HEAD 未改变且暂存区为空时重新执行测试，不重复写业务代码。
- 服务端变更操作串行执行，并发请求返回 HTTP 409。
- 桌面界面提供 ask/task/auto 模式选择，但实际写入仍需要明确确认，不能理解为已开放无人值守修改。

Git 提交失败、进程中断和新项目失败的自动恢复尚未实现。不自动回滚用户文件。

## 9. 桌面与运行管理

- 支持浏览器开发界面和 Tauri 桌面窗口。
- 桌面端检测本地健康服务，已有服务则复用，否则启动 Python 子进程。
- 退出时仅结束自身启动的服务进程。
- 可通过 CODEAGENT_ROOT、CODEAGENT_PYTHON 指定源码根目录和解释器。

当前桌面构建仍依赖 Python 与服务源码环境，不是已经携带完整后端运行时的独立安装包；桌面人工验收未完成。

## 12. 使用与安全边界

- 模型源码、测试和 Maven 依赖在本机执行，没有沙箱隔离，应先审核后授权。
- 连接外部模型会发送需求、文档或源码，需自行确认数据使用政策。
- 本地 HTTP 服务尚无用户身份认证，且允许跨域；不要作为对外共享服务部署。
- 密钥使用本地环境变量，实际配置与 data 目录已忽略，不应将密码或 Token 写进文档和仓库。
- 建议先在临时目录和专用测试仓库使用，不直接对重要未备份项目执行首次验证。
